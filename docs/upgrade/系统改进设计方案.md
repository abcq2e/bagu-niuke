## 二、P1 — 响应延迟优化

### 2.1 根因分析

当前 `QuizApp.doUnifiedChat` 在 SSE 流开始推送之前，执行了大量串行同步操作：

```
用户消息到达
  │
  ├─ [串行] queryRewriter.doQueryRewrite()  ← LLM 调用，约 1-2s
  ├─ [串行] webFuture（联网搜索）           ← 超时 1.5s
  ├─ [串行] topicDocumentCache.getMixedQuestions()
  ├─ [串行] baguFuture + mianzhaFuture（RAG 双路检索）← 约 2-3s
  └─ [串行] LLM 流式推送（等上面都完成才开始）
```

虽然代码里有 `CompletableFuture`，但 `rewriteFuture.join()` 和 `webFuture.getNow("")` 仍然是阻塞式等待，本质上还是串行。整个"准备阶段"需要 **4-6 秒**，之后才开始推第一个 token。

### 2.2 改进目标

首 token 延迟（TTFT）从 **~10s 降至 ~2s**。

### 2.3 改进方案：并行预热 + 流式边检索边生成

#### 方案 A：纯并行化（低风险，快速落地）

```
用户消息到达
  ├── [并行 1] queryRewriter（LLM 改写）
  ├── [并行 2] 联网搜索（固定 1s 超时）
  ├── [并行 3] topicDocumentCache（内存，几乎 0 延迟）
  └── [并行 4] RAG 双路检索（向量检索，约 300-500ms）

allOf([1,2,3,4]).join() ← 总耗时 = max(各任务)，而非 sum
  └── LLM 流式推送（首 token 2-3s）
```

具体改动：
- 将 `rewriteFuture.join()` 改为与其他 Future 真正并行，`allOf` 统一等待
- RAG 检索超时从"无限等待"改为 **1000ms**，超时则用空结果继续
- 联网搜索超时从 1500ms 降为 **800ms**（面试场景时效性要求不高）

#### 方案 B：渐进式上下文注入（中等风险，体验更优）

核心思路：**先用基础上下文让 LLM 开始生成，再用补充检索结果动态追加**。

```
阶段 1（0ms）：立即用方向文档（内存缓存）+ system prompt 开始 LLM 流式生成
阶段 2（异步）：RAG 检索、联网搜索在后台跑
阶段 3（300-500ms）：将补充检索结果通过 advisor 或追加消息注入到对话记忆，影响下一轮
```

此方案需要重构 ChatClient 调用，实现复杂度较高，建议作为 V2 版本。

#### 推荐实施方案（P1）

**第一期：方案 A（纯并行化）+ 降低超时**

```java
// 改造后的 doUnifiedChat 关键流程（伪代码）

// 1. 方向信息从内存取（0延迟，移到最前）
String topic = topicRotationService.currentTopic(chatId);
List<Document> topicDocs = topicDocumentCache.getMixedQuestions(topic, 4); // 内存

// 2. 真正并行执行3个 IO 操作
CompletableFuture<String> rewriteFuture = CompletableFuture.supplyAsync(
    () -> queryRewriter.doQueryRewrite(message)
).orTimeout(2000, MILLISECONDS).exceptionally(e -> message);

CompletableFuture<String> webFuture = CompletableFuture.supplyAsync(
    () -> webSearchTool.searchWeb(message)
).orTimeout(800, MILLISECONDS).exceptionally(e -> "");

CompletableFuture<List<Document>> ragFuture = CompletableFuture.supplyAsync(
    () -> ragSearch(rewriteFuture.join(), topic)    // ← 可以用 message 代替改写结果先跑
).orTimeout(1000, MILLISECONDS).exceptionally(e -> List.of());

// 3. 并行等待（总耗时 ≈ max，而非 sum）
CompletableFuture.allOf(webFuture, ragFuture).join();

// 4. 立即开始 LLM 流
buildContextAndStream(...);
```

**预期效果：**
- 总准备时间：max(800ms, 1000ms) = ~1s（原来 4-6s）
- 首 token 延迟：~2-3s（原来 8-10s）

## 三、P2 — 流式卡顿优化

### 3.1 根因分析

"走走停停"现象通常由以下原因之一或叠加导致：

**后端侧（主要原因）：**
1. **Reactor 背压阻塞**：`Flux.create` 内部订阅了 Spring AI 的 `.stream().content()`，如果下游（SSE 写入）比上游（AI token 生成）慢，会产生积压
2. **`doOnNext` 中同步操作**：每个 chunk 都调用 `fullTextBuilder.append(chunk)` 是串行的，虽然轻量，但如果 `connectingStatus` 刷新、画像刷新等操作混在同一线程里会造成竞争
3. **AI 模型本身的 thinking 停顿**：DeepSeek 等部分模型在生成长推理链时会有内部停顿，这是模型行为，无法彻底消除，但可以优化用户感知

**前端侧（次要原因）：**
1. **每个 chunk 都触发 `cacheMessages`**：在 `onmessage` 里每收到一个 token 就调用 `cacheMessages(chatId.value, [...messages.value])`，这会创建新数组并写入，在长对话中每帧操作 O(n) 数据
2. **每个 chunk 都调用 `extractDirection`**：正则匹配虽轻，但在高频 chunk 下累积
3. **`scrollDown()` 每帧触发 `nextTick`**：高频 nextTick 排队会让 Vue 渲染调度压力增大

### 3.2 改进方案

#### 后端改进

**方案 1：切换到 Spring AI 原生 Flux 管道，去掉 `Flux.create` 包装层**

```java
// 当前写法（有不必要的 create 包装）：
return Flux.<String>create(emitter ->
    chatClient.prompt()...stream().content()
    .doOnNext(chunk -> { fullTextBuilder.append(chunk); emitter.next(chunk); })
    .subscribe()
);

// 改进写法（直接使用原生 Flux）：
return chatClient.prompt()
    .user(message)
    .system(enhancedSystem.toString())
    .advisors(...)
    .stream()
    .content()
    .doOnNext(chunk -> fullTextBuilder.append(chunk))    // 只保留轻量操作
    .doOnComplete(() -> {
        // 流结束后的处理，不在关键路径上
        handleStreamComplete(chatId, fullTextBuilder.toString());
    })
    .map(chunk -> chunk.replace("[NEXT_TOPIC]", "").replace("\r\n", "\n"));
```

**方案 2：为 SSE 响应显式设置 Reactor Scheduler**

```java
// 在 Controller 层将 Flux 切换到弹性线程池，避免阻塞 Netty IO 线程
return quizApp.doUnifiedChat(message, finalChatId)
    .subscribeOn(Schedulers.boundedElastic())
    .publishOn(Schedulers.boundedElastic());
```

**方案 3：Thinking 模型停顿处理**

如果使用的是 DeepSeek-R1 等 thinking 模型，建议：
- 将 `<think>...</think>` 内容过滤掉，不推送给前端
- 或推送一个特殊标记让前端显示"思考中"状态，等 `</think>` 后才显示正文

#### 前端改进

**方案 1：批量更新缓存（节流）**

```javascript
// 当前：每个 chunk 都写缓存（高频 O(n)）
eventSource.onmessage = (e) => {
  if (e.data && e.data !== '[DONE]') {
    messages.value[aiIdx].content += e.data
    cacheMessages(chatId.value, [...messages.value])  // ← 每帧都写
    scrollDown()                                        // ← 每帧都触发
  }
}

// 改进：用 requestAnimationFrame 或节流，每 100ms 批量写一次
let pendingCache = false
eventSource.onmessage = (e) => {
  if (e.data && e.data !== '[DONE]') {
    messages.value[aiIdx].content += e.data
    // 节流缓存写入
    if (!pendingCache) {
      pendingCache = true
      setTimeout(() => {
        cacheMessages(chatId.value, [...messages.value])
        pendingCache = false
      }, 200)
    }
    // 节流滚动
    if (!pendingScroll) {
      pendingScroll = true
      requestAnimationFrame(() => {
        scrollDown()
        pendingScroll = false
      })
    }
  }
}
```

**方案 2：`extractDirection` 只在 chunk 包含【时才执行**

```javascript
// 当前：每个 chunk 都执行正则
extractDirection(e.data)

// 改进：短路判断
if (e.data.includes('【')) {
  extractDirection(e.data)
}
```

**方案 3：消息缓存使用 WeakRef 或 LRU 结构**

当前 `messageCache` 是普通对象，每次 `cacheMessages` 创建 `[...messages.value]`（展开新数组），在消息数量多时内存和 CPU 都有压力。可以改为只存消息引用，不做深拷贝。

## 四、P3 — 能力画像持久化 + 打分合理性

### 4.1 根因分析

**问题 1：数据不持久化**

`UserAbilityService` 中 `profiles` 是纯内存 `ConcurrentHashMap`：

```java
private final Map<String, UserAbilityProfile> profiles = new ConcurrentHashMap<>();
```

服务重启后数据全部丢失。没有任何 DB/Redis/文件持久化。

**问题 2：打分系统不合理**

现有评分存在以下问题：

1. **LLM 自主打分，缺乏约束**：SCORE_PROMPT 虽然定义了 1-5 分标准，但 LLM 倾向给高分（"善意偏差"），导致分数虚高
2. **问题与回答的关联性弱**：`lastAiQuestions` 只保存 AI 回复的前 200 字，可能截断了关键问题内容，评分依据不完整
3. **指数加权移动平均（EWMA）参数偏保守**：`score = score * 0.7 + (newScore/5*100) * 0.3`，历史权重 70% 过高，导致新表现对分数影响太小（答错了分也降不下去）
4. **JSON 解析使用自制正则**：容易因 LLM 输出格式轻微变化而解析失败，默默吞错、使用默认值 3，导致"无效评分"频繁发生
5. **topic 字段由 LLM 自由填写**：可能写 "Java并发编程" 而不是系统定义的 "Java并发"，导致方向不匹配、画像出现重复方向

### 4.2 改进方案

#### 持久化方案

**选项 1：Redis（推荐，已有 Redis 依赖）**

```java
// UserAbilityService 改造

@Service
public class UserAbilityService {
    
    @Resource
    private RedisTemplate<String, Object> redisTemplate;
    
    private static final String PROFILE_KEY_PREFIX = "ability:profile:";
    private static final long PROFILE_TTL_DAYS = 30;
    
    // 内存缓存（一级缓存）
    private final Map<String, UserAbilityProfile> localCache = new ConcurrentHashMap<>();
    
    public UserAbilityProfile getOrCreateProfile(String chatId) {
        // 先查本地缓存
        return localCache.computeIfAbsent(chatId, id -> {
            // 再查 Redis
            String key = PROFILE_KEY_PREFIX + id;
            UserAbilityProfile cached = (UserAbilityProfile) redisTemplate.opsForValue().get(key);
            return cached != null ? cached : new UserAbilityProfile(id);
        });
    }
    
    public void saveProfile(String chatId) {
        UserAbilityProfile profile = localCache.get(chatId);
        if (profile != null) {
            String key = PROFILE_KEY_PREFIX + chatId;
            redisTemplate.opsForValue().set(key, profile, PROFILE_TTL_DAYS, TimeUnit.DAYS);
        }
    }
    
    // 评分后自动保存
    public CompletableFuture<Void> scoreAnswerAsync(...) {
        return CompletableFuture.runAsync(() -> {
            // ...评分逻辑...
            profile.updateTopicScore(topic, score, weakPoints);
            saveProfile(chatId);  // 异步保存到 Redis
        });
    }
}
```

**选项 2：文件持久化（与 FileBasedChatMemory 风格一致，无额外依赖）**

将 `UserAbilityProfile` 序列化为 JSON 文件，路径为 `${chat-memory.dir}/profile_{chatId}.json`。

#### 打分合理性改进

**改进 1：topic 字段改为由系统固定，不让 LLM 自由填写**

```java
// SCORE_PROMPT 修改：告知 LLM 方向已固定
private String buildScorePrompt(String topic, String question, String answer) {
    return """
        你是技术面试评分系统。根据面试官的问题和候选人的回答，给出评分。
        
        当前考察方向（固定，请直接返回此值）：%s
        面试官问题：%s
        候选人回答：%s
        
        打分要求：请严格按以下标准，宁可低估不要高估：
        1分 - 回答完全错误或无关
        2分 - 知道概念但有明显错误
        3分 - 基本正确，缺少关键细节
        4分 - 掌握较好，能说出原理
        5分 - 全面深入，覆盖边界情况和实战经验
        
        请返回 JSON：{"score":整数1-5, "topic":"%s", "weakPoints":["薄弱点1","薄弱点2"], "comment":"一句评价"}
        """.formatted(topic, question, answer, topic);
}
```

**改进 2：使用 Jackson 解析 JSON，替换自制正则**

```java
@Resource
private ObjectMapper objectMapper;

// 解析评分结果
private ScoreResult parseScoreResult(String json, String defaultTopic) {
    try {
        // 提取 JSON 块（LLM 可能在 JSON 前后加解释文字）
        int start = json.indexOf('{');
        int end = json.lastIndexOf('}');
        if (start >= 0 && end > start) {
            String jsonStr = json.substring(start, end + 1);
            return objectMapper.readValue(jsonStr, ScoreResult.class);
        }
    } catch (Exception e) {
        log.warn("评分 JSON 解析失败，使用默认值: {}", e.getMessage());
    }
    return new ScoreResult(3, defaultTopic, List.of(), "解析失败");
}
```

**改进 3：调整 EWMA 参数，增大近期权重**

```java
// 当前：history 70% + new 30%（历史惯性过大）
this.score = (int) Math.round(this.score * 0.7 + (newScore / 5.0 * 100) * 0.3);

// 改进：动态权重（题数少时新题影响大，题数多时趋于稳定）
// questionCount <= 3 时用 0.5，之后逐渐降到 0.3
double newWeight = Math.max(0.3, 0.6 - questionCount * 0.1);
double histWeight = 1.0 - newWeight;
this.score = (int) Math.round(this.score * histWeight + (newScore / 5.0 * 100) * newWeight);
```

**改进 4：保存完整问题上下文**

```java
// 当前：只保存 AI 回复前 200 字
lastAiQuestions.put(chatId, cleanFull.length() > 200 ? cleanFull.substring(0, 200) : cleanFull);

// 改进：保存 {topic, question} 结构化信息

    userAbilityService.scoreAnswerAsync(chatId, ctx.topic(), ctx.question(), message);
}
```

## 五、P4 — 能力画像 UI 重设计 + 薄弱点导向考察

### 5.1 根因分析

**UI 问题：**
- 当前布局：左侧栏（260px）+ 主对话区（flex:1）+ 右侧能力画像（240px）
- 三栏布局导致中间对话区宽度被严重压缩，在 1280px 屏幕下只剩约 780px
- 雷达图本身只有 220×220px，放在 240px 侧边栏里使用率极低

**薄弱点考察问题：**
- `UserAbilityService.getTopicWeight()` 虽然实现了权重计算，`TopicRotationService.shuffledWithWeights()` 也实现了加权排序
- 但**薄弱点具体知识点**（如"CAS 原理"、"锁升级流程"）没有影响出题内容，只影响方向顺序
- 即使知道用户"CAS 原理"薄弱，下一轮出的题也可能是任意 Java 并发题目

### 5.2 改进方案

#### UI 重设计：折叠式抽屉面板

**设计原则：** 能力画像是辅助功能，不应占据主界面空间；对话是核心，应给予最大空间。

**改进后布局：**

```

│  会话列表     │   消息区域                            │按钮  │

│               │                                       │      │
│               │   输入框                              │      │

```

- 移除右侧固定 240px 侧边栏
- 改为右下角浮动按钮「📊 能力画像」，点击后以**抽屉（Drawer）或模态框（Modal）**弹出
- 抽屉从右侧滑入，宽度 360px，覆盖在内容上方（不挤压布局）

#### 薄弱点导向考察：深度改进

**当前问题：** 薄弱点列表存在，但出题时只影响方向顺序，具体题目内容不受影响。

**改进方案：将薄弱点具体知识点注入出题上下文**

```java
// QuizApp.doUnifiedChat 中，在构建 context 时强化薄弱点注入
String weakHint = userAbilityService.buildWeakPointHint(chatId, topic);

// 当前 buildWeakPointHint 只是简单提示
// 改进后：提供结构化的薄弱点出题指令

public String buildWeakPointHint(String chatId, String topic) {
    UserAbilityProfile.TopicScore ts = getTopicScore(chatId, topic);
    if (ts == null || ts.getScore() >= 70) return "";
    
    List<String> weakPoints = ts.getWeakPoints();
    StringBuilder sb = new StringBuilder();
    
    sb.append("🎯 个性化出题指令：\n");
    sb.append("该用户在【").append(topic).append("】方向掌握度为 ")
      .append(ts.getScore()).append("/100（").append(scoreLevel(ts.getScore())).append("）\n");
    
    if (!weakPoints.isEmpty()) {
        sb.append("已知薄弱知识点（优先考察这些，并深度追问）：\n");
        for (int i = 0; i < weakPoints.size(); i++) {
            sb.append(i + 1).append(". ").append(weakPoints.get(i)).append("\n");
        }
        sb.append("→ 请针对以上薄弱点出题，不要跳过，直到用户能回答清楚为止。\n");
    }
    
    return sb.toString();
}
```

**保留知识点轮询扫描的同时加入薄弱点强化**

两种模式并存，通过规则控制：

```
模式 A：全量扫描（默认）
  - TopicRotationService 按加权顺序轮转 16 个方向
  - 每个方向考察 3-4 题后切换（已有机制保留）
  
模式 B：薄弱点强化（触发条件）
  - 当某方向得分 < 40 分时，在该方向内优先出薄弱点相关题目
  - 通过 buildWeakPointHint 将具体薄弱点注入 System Prompt
  - 不改变方向轮转机制，只影响该方向内的出题内容
```

**薄弱点积累机制优化**

当前薄弱点只保留最近 5 个，且按追加顺序。改进为按出现频率排序：

```java
// UserAbilityProfile.TopicScore 中的薄弱点管理

// 改进：用 Map 记录每个薄弱点的出现次数
private final Map<String, Integer> weakPointFreq = new LinkedHashMap<>();

void update(int newScore, List<String> newWeakPoints) {
    // ...评分更新...
    
    if (newWeakPoints != null) {
        for (String wp : newWeakPoints) {
            weakPointFreq.merge(wp, 1, Integer::sum);
        }
        // 按频次排序，保留 top 8
        this.weakPoints = weakPointFreq.entrySet().stream()
            .sorted(Map.Entry.<String, Integer>comparingByValue().reversed())
            .limit(8)
            .map(Map.Entry::getKey)
            .collect(toList());
    }
}
```

## 八、风险与注意事项

1. **Redis 序列化**：`UserAbilityProfile` 需要实现 `Serializable` 或配置 Jackson 序列化，避免反序列化失败
2. **并行化超时调优**：800ms/1000ms 超时在网络条件差时可能频繁降级，需要结合实际环境调整，建议可配置化（`application.yml`）
3. **抽屉 UI 移动端适配**：在小屏设备上，360px 抽屉可能过宽，需要设计响应式宽度（`width: min(360px, 100vw)`）
4. **薄弱点注入可能影响系统 prompt 长度**：如果薄弱点过多，context 长度会增加，注意 token 消耗，建议薄弱点最多注入 3 个
5. **TopicRotationService 状态与持久化的一致性**：轮转状态目前也是内存，服务重启后方向顺序会重置；如果将画像持久化而轮转状态不持久化，会出现"画像显示 Java并发 弱，但重启后第一个考察的可能仍是 Java基础"的问题，建议一期先接受这个不一致，二期再考虑是否也持久化轮转状态
