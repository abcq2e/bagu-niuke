# 面试官全面考察改造 — 后端设计方案

> 目标：让 QuizApp 面试官的考察方向**全面且确定性覆盖**，不再只在 Java 基础 / Redis / MySQL 之间打转。
> 本文档是完整实施说明书，交给任意开发者/模型可直接照做。所有行号基于当前工作区代码。

---

## 一、问题诊断（为什么会偏科）

偏科不是 System Prompt 一处的问题，是整条出题链路叠加的结果：

| # | 病因 | 位置 |
|---|------|------|
| 1 | **轮转索引是全局共享的**：`rotationIndex` 是应用级 `AtomicInteger`，所有会话共用一个计数器。单个会话看到的方向是随机断片，重启归零。会话级覆盖状态不存在。 | `QuizApp.java:97` |
| 2 | **轮转检索命中不了目标方向**：`KB_ROTATION_QUERIES`（`QuizApp.java:81`）用关键词做向量检索（阈值 0.3），但 130KB 大文档被切成小 chunk，一个 chunk 混多个方向的题，查"Docker"返回的可能一半是 MySQL 题。 | `QuizApp.java:81-94, 172-182` |
| 3 | **预加载题库天然偏科**：`loadQuestionBankInternal()`（`QuizApp.java:345`）26 个种子关键词 Java 系排最前，注入时截断到前 2000 字符（`QuizApp.java:209`），截断后剩下的全是 Java 核心内容。 | `QuizApp.java:207-213, 345-378` |
| 4 | **用户相关 RAG 正反馈**：用户答 HashMap → 检索回更多 HashMap 文档 → 越问越集中。 | `QuizApp.java:216-228` |
| 5 | **Prompt 计数规则无状态支撑**："每 10 题同方向不超过 4 题" 要求 AI 自己记历史，但 ChatMemory 是滑动窗口，AI 数不清。 | `QuizApp.java:48-72` |

**核心结论：方向覆盖必须由代码层的确定性状态保证（会话级轮转 + 元数据精确过滤检索），不能指望 LLM 自觉。**

### 任务 4：新建 TopicRotationService（核心）

新文件 `src/main/java/com/yupi/yuaiagent/app/TopicRotationService.java`，`@Component`。

**职责**：维护每个会话（chatId）的方向覆盖状态，保证一轮内 16 个方向不重不漏，轮完重新洗牌进入下一轮。

**关键设计——方向推进不能按消息数走**：面试是"出题→回答→追问 L2→回答→追问 L3…"的流程，一个方向要停留多条消息。如果每条用户消息都换方向，追问期间方向就被白白消耗，16 轮实际只考了一半方向。因此方向推进由两个信号驱动：
- **AI 主动信号**：System Prompt 要求 AI 在"该方向考察完毕（追问到 L4 或候选人答不上来）"时，在回复末尾输出标记 `[NEXT_TOPIC]`。代码检测到标记 → 推进方向（标记在返回前端前删除）。
- **硬上限兜底**：同一方向连续 4 条用户消息后强制推进（防止 AI 忘输出标记导致卡在一个方向）。

```java
@Component
public class TopicRotationService {

    /** 必须与 document 目录下 八股-*.md 的方向名逐字一致 */
    public static final List<String> TOPICS = List.of(
            "Java基础与集合", "Java并发", "JVM", "Spring框架",
            "MySQL", "Redis", "消息队列", "计算机网络",
            "操作系统与Linux", "分布式与微服务", "算法与数据结构", "设计模式",
            "系统设计与场景", "Docker与运维", "ES与搜索", "Agent与AI应用");

    /** 同一方向最多停留的用户消息数（追问预算），超过则强制换方向 */
    private static final int MAX_EXCHANGES_PER_TOPIC = 4;

    private final Map<String, SessionState> sessions = new ConcurrentHashMap<>();

    /** 会话状态（所有字段访问都在 synchronized(state) 内，无需 volatile） */
    private static class SessionState {
        final Deque<String> remaining;   // 本轮剩余方向（构造时 new ArrayList<>(TOPICS) → shuffle → 入队）
        final List<String> covered;      // 本轮已考察完的方向（供 prompt 展示）
        String currentTopic;             // 当前方向（构造时弹出第一个）
        int exchangesOnCurrent;          // 当前方向已进行的用户消息数
        long lastAccess;
    }

    /**
     * 每条用户消息调用一次：返回当前方向并计数。
     * 若 exchangesOnCurrent 已达 MAX_EXCHANGES_PER_TOPIC，先内部推进再返回新方向。
     * remaining 弹空后：covered 清空、重新洗牌全部方向、开始新一轮。
     */
    public String currentTopic(String chatId) { ... }

    /** AI 输出了 [NEXT_TOPIC] 标记时调用：当前方向计入 covered，弹出下一个方向。幂等（重复调用只推进一次可不保证，但同一响应只触发一次调用）。 */
    public void advance(String chatId) { ... }

    /** 本轮已考察完的方向（不含当前方向），用于注入 prompt */
    public List<String> coveredTopics(String chatId) { ... }

    /** 定时清理：@Scheduled(fixedDelay = 30 * 60 * 1000)，移除 lastAccess 超过 2 小时的会话 */
    public void evictExpiredSessions() { ... }
}
```

实现要点：
- 并发安全：`sessions.computeIfAbsent(chatId, ...)` 创建状态；**所有对单个 `SessionState` 字段的读写都包在 `synchronized(state)` 块内**（锁粒度是单会话，不同会话互不阻塞）。方法签名上**不要**加 `synchronized`（那会锁整个 service）。
- 洗牌用 `Collections.shuffle(list)`（无需固定种子）。
- `@Scheduled` 需要启动类有 `@EnableScheduling`，检查 `YuAiAgentApplication.java`，没有则加上。
- **不要**从向量库动态查方向列表（启动顺序耦合、查询成本高），硬编码常量即可，加注释说明与文件名的一致性约束。

### 任务 5：QuizApp 检索链路改造

**5.2 新增方向检索**（替换第 141-143 行 + 第 172-182 行的轮转逻辑）：

```java
@Resource
private TopicRotationService topicRotationService;

// doUnifiedChat 内：
String topic = topicRotationService.currentTopic(chatId);
List<String> covered = topicRotationService.coveredTopics(chatId);

// 精确过滤检索：topic 元数据 == 本轮方向，命中率 100%
CompletableFuture<List<Document>> topicDocsFuture = CompletableFuture.supplyAsync(() -> {
    try {
        List<Document> docs = quizVectorStore.similaritySearch(SearchRequest.builder()
                .query(topic + " 面试题")          // query 仅用于排序，过滤靠 filter
                .topK(10)
                .similarityThreshold(0.0)          // 过滤已保证方向正确，不需要阈值
                .filterExpression(new FilterExpressionBuilder()
                        .eq("topic", topic).build())
                .build());
        Collections.shuffle(docs);                 // 打乱 chunk，避免每次都注入同一段
        return docs.stream().limit(4).toList();
    } catch (Exception e) {
        log.warn("方向检索失败 [{}]: {}", topic, e.getMessage());
        return List.<Document>of();
    }
});
```

**5.3 检测 [NEXT_TOPIC] 标记并推进方向**：`doUnifiedChat` 的流式返回已有 `reduce` 把全量响应聚合成一个字符串（第 252-263 行），在其后的 `.map(...)`（第 264 行）中加标记处理：


### 任务 6：System Prompt 瘦身

替换 `QuizApp.java:48-72` 的 `SYSTEM_PROMPT`，删除 AI 做不到的计数规则（"每 10 题不超过 4 题"、"连续 3 题偏科"），方向控制已由代码保证：

```text
你是大厂技术面试官。每轮对话下方都会注入【本轮必考方向】和该方向的牛客真实面经题目。

🔴 出题规则
1. 新题必须出自【本轮必考方向】注入的题目，禁止自选方向。
2. 深度追问：L1 表面 → L2 原理 → L3 源码/实战。同一道题最多追问到 L3。
3. 当前方向考察完毕的判定：追问触达候选人边界（答不上来或答得很浅），或已问过 2 道该方向的题。
   判定成立时，在回复的最末尾输出标记 [NEXT_TOPIC]（原样输出这 12 个字符，系统会处理，候选人看不到）。
4. 已考察过的方向禁止再出新题（追问除外）。

🔴 行为准则
禁止：空洞夸赞 / 给选择题 / 一次性问多个问题
每次回复：
① 简短评价（答得怎么样、漏了什么）
② 答不上来 → 150 字讲解（①②③分条）；答对了 → 直接追问或出新题
③ 出题（需要换方向时先输出 [NEXT_TOPIC]，下一轮系统会注入新方向）
输出风格：自然对话。代码用```java```或```sql```，重要概念**粗体**。
```

> 注意：AI 输出 `[NEXT_TOPIC]` 后，**下一条**用户消息到来时才会注入新方向的题目，所以标记出现的那轮回复里 AI 应当只做点评/收尾提问，不出跨方向的新题。若发现 AI 经常在标记同一轮就自编新方向的题，可在规则 3 补一句"输出标记的那轮不要出新题，等下一轮注入"。
