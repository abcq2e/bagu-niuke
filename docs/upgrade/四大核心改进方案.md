# AI 面试官系统四大核心改进方案

> 本文档针对用户反馈的四个问题，结合当前代码现状，给出具体改进方案。参考了 [floating-ui](https://floating-ui.com/)、[vue-draggable-plus](https://github.com/Alfred-Skyblue/vue-draggable-plus)、[AgileCoder](https://github.com/FSoft-AI4Code/AgileCoder) 等开源项目的设计思路。

---

## 问题一：能力面板浮动按钮（FAB）可以拖拽移动

### 现状分析

`ChatView.vue` 中的 `.ability-fab` 按钮固定在右下角 `position: fixed; right: 20px; bottom: 100px`，用户无法移动，容易遮挡消息内容。

### 改进方案

**方案：纯 CSS + 原生 Pointer Events 实现可拖拽 FAB（参考 [Vue Draggable](https://github.com/SortableJS/vue.draggable.next) 的事件处理思路）**

核心思路：
1. 给 FAB 按钮添加 `@pointerdown` 事件，记录初始坐标
2. 在 `pointermove` 时更新按钮的 `top`/`left` 定位（切换为 `position: fixed; top: Y; left: X`）
3. `pointerup` 时释放事件，判断是否为"点击"（位移 < 5px 才触发打开面板）
4. 用 `localStorage` 持久化最后一次位置，刷新页面后恢复

**⚠️ CSS 层级注意事项：**

`.ability-fab` 当前使用 `position: fixed; right: 20px; bottom: 100px`，改为拖拽后需要切换为 `position: fixed; left: Xpx; top: Ypx`（同时去掉 `right/bottom`）。`fixed` 定位相对于视口，不受父容器 `.main` 影响，这一点是安全的。但要注意 **`transform` 属性会创建新的包含块**，如果父元素上有 `transform`（例如抽屉动画的 `translateX`），会导致 `fixed` 定位失效、FAB 跟着抽屉移动。需要确认 `.ability-drawer` 动画结束后不残留 `transform`。

**关键代码逻辑（伪代码描述）：**

```
const fabPos = reactive({ x: window.innerWidth - 68, y: window.innerHeight - 148 })
const isDragging = ref(false)
let dragStart = { x: 0, y: 0, bx: 0, by: 0 }

onPointerDown(e):
  isDragging = true
  dragStart = { x: e.clientX, y: e.clientY, bx: fabPos.x, by: fabPos.y }
  document.addEventListener('pointermove', onPointerMove)
  document.addEventListener('pointerup', onPointerUp)

onPointerMove(e):
  fabPos.x = clamp(dragStart.bx + e.clientX - dragStart.x, 0, window.innerWidth - 56)
  fabPos.y = clamp(dragStart.by + e.clientY - dragStart.y, 0, window.innerHeight - 56)

onPointerUp(e):
  const didMove = Math.abs(e.clientX - dragStart.x) > 5 || Math.abs(e.clientY - dragStart.y) > 5
  if (!didMove) showAbilityPanel = true   // 区分拖拽和点击
  savePositionToLocalStorage(fabPos)
  isDragging = false
```

**边界处理：**
- 拖到屏幕边缘时吸附（clamp 限制范围）
- 窗口 resize 时重新校验位置，防止超出可视区
- 移动端适配（touch 转 pointer 事件，`touch-action: none` 防止滚动冲突）

**预期效果：** 用户可以将 FAB 拖拽到任意位置，下次打开页面时自动恢复位置。

## 问题二：面试官回复速度偏慢

### 现状分析

`QuizApp.doUnifiedChat()` 中三路 IO 是**真正并行**的（`CompletableFuture.allOf`），总耗时 = max(各路超时)，不是串行叠加。实际瓶颈是：
1. **联网搜索对面试场景价值低**，但其 800ms 超时会拉长整体等待（当其他两路比它快时）
2. **查询改写虽然并行**，但它占用一个线程池槽位，且 `rewriteFuture.getNow(message)` 在 RAG 启动前调用，若改写还没完成会拿到原始消息——说明改写和 RAG 之间存在隐式的软依赖
3. **评分调用用的是主模型**（同一个 `chatClient`），异步虽不阻塞响应，但会抢占 API 并发配额，间接影响主对话速度

### 改进方案

**方案 A：禁用联网搜索（最快，推荐优先落地）**

面试题考察的是固定知识点，不需要实时搜索。去掉 `webFuture` 可以让 `CompletableFuture.allOf` 等待时间从 max(2s,800ms,1s) 降低到 max(2s,1s)，但更关键的是减少了一次网络调用带来的不确定延迟。

**方案 B：评分使用轻量 Prompt 或小模型**

`SCORE_PROMPT` 当前调用主模型 `chatClient`（DeepSeek），可以：
- 将评分 Prompt 压缩到 50 字以内（去掉详细评分标准说明）
- 或配置单独的轻量评分客户端（如 `deepseek-chat` 速度比 `deepseek-reasoner` 快 3-5 倍）

**方案 C：取消查询改写（Quiz 场景收益有限）**

面试场景下用户消息都是短句回答，查询改写对 RAG 召回提升有限。

**⚠️ 注意：** 查询改写和 RAG 是并行的（`CompletableFuture` 真正并行），去掉它并不能缩短总等待时间（RAG 的 1s 超时本来就更长）。真正的收益是：① 减少一次 LLM API 调用，降低并发配额压力；② 去掉 `rewriteFuture.getNow(message)` 对改写结果的软依赖，让 RAG 始终用原始消息检索，逻辑更清晰。**预期直接提速效果有限，主要是减少资源消耗。**

**整体优化后预期提速：** 方案 A（去掉联网搜索）是最有效的，可让首 Token 延迟从约 2-3s 降至 1-1.5s（消除 800ms 的不确定等待）。方案 B（评分轻量化）减少 API 配额竞争，间接提速。方案 C 主要是减资源消耗而非直接提速。

**方案 D：题目文档不做 RAG，只做方向文档注入**

当前已有 `topicDocumentCache.getMixedQuestions(topic, 4)` 从缓存取方向题目（零延迟），但仍然在做 RAG 检索（`multiQuerySearchService.multiQuerySearchWithCategory`）。对于"出题"这个任务，方向缓存题目已经足够，RAG 仅在"评分点评"时有价值。可以将 RAG 检索降低为 2 条（减少 Embedding 查询次数）。

## 问题三：面试官考察知识点重复度高，覆盖不全

### 现状分析（核心问题）

当前方向轮转机制在 `TopicRotationService` 中，每个方向出题依靠 `topicDocumentCache.getMixedQuestions(topic, 4)` 随机取 4 道题，**但没有任何跨轮次的已问题目去重机制**。

具体问题：
1. `shuffledWithWeights()` 每轮重新洗牌，但方向内的题目每次都是**随机取 4 道**，可能重复
2. `MAX_EXCHANGES_PER_TOPIC = 4` 每个方向只问 4 轮就强制换方向，方向内考察深度不足
3. 评分时 `topic` 字段依赖 AI 自己返回（`SCORE_PROMPT` 中 `"topic":"{topic}"`），AI 可能返回不属于该方向的 topic（如将 Redis 的 AOF 问题归到 JVM）
4. System Prompt 中没有明确的**知识点维度清单**，AI 出题时自由度过大，容易反复问同类题

### 改进方案

#### 3.1 题目去重：追踪 AI 实际提问的内容

参考 [AI-Interview-System](https://github.com/Yuanrui-Mdt-Info/aiinterviewer) 的已问题目追踪思路：

在 `TopicRotationService.SessionState` 中增加：
```java
final Set<String> askedQuestionFingerprints = new HashSet<>();  // 已问题目指纹（AI 回复中提取）
```

**⚠️ 去重对象必须是 AI 实际问出的题，而不是注入给 AI 的候选题。**

原因：每轮注入 4 道候选题，AI 只会从中挑 1-2 道问。如果把注入的 4 道全标记为"已问"，会导致题目空间快速耗尽（每轮浪费 2-3 道题），后期出题越来越窄直至无题可出。

**正确做法（两步）：**

**第一步：从 AI 回复中提取实际提问的题目指纹。**  
在 `doOnComplete()` 里，从 `fullTextBuilder.toString()` 中提取 AI 本轮的提问句（以"？"结尾的句子，取前 40 个字做指纹），写入 `askedQuestionFingerprints`。

**第二步：在 `getMixedQuestions()` 中过滤已问题目。**  
取题目时，将候选题与 `askedQuestionFingerprints` 做相似度比对（简单字符串包含即可，不需要向量相似），排除匹配的题。全部排完才允许重复。

这样每道题真正被 AI 问出后才标记，不会误判未问的候选题。

#### 3.2 考察维度显式化：给每个方向定义知识点子维度

以 JVM 为例，当前只知道"要考 JVM"，但不知道要考哪些维度。参考 [JavaGuide](https://github.com/Snailclimb/JavaGuide) 的知识体系结构，为每个方向定义必考维度清单，注入 System Prompt：

```
JVM 必考维度（共 8 个，每次面试每个维度至少出 1 题）：
1. 内存结构（堆/栈/方法区/元空间）
2. 垃圾回收算法（标记清除/标记整理/复制）
3. 垃圾收集器（CMS/G1/ZGC）
4. 类加载机制（双亲委派）
5. JVM 参数调优
6. 内存泄露排查
7. GC 日志分析
8. 字节码与 JIT 编译
```

在后端维护一个 `TopicDimensions` 常量类，每次注入当前方向的维度清单和**已覆盖的维度**，AI 会自动选择未覆盖的维度出题。

#### 3.3 修复 topic 归属错误问题

**根本原因：** `SCORE_PROMPT` 中写的是 `"topic":"{topic}"` 让 AI 返回 topic，但 AI 有时会"聪明地"根据题目内容修改 topic（如把 Redis AOF 问题的回答归到错误的分类）。

**修复方案：**
- 在 `parseScoreResult()` 中，不管 AI 返回什么 topic，**强制用 `defaultTopic`（即后端传入的真实方向）覆盖**
- 当前代码中 `if (sr.getTopic() == null || sr.getTopic().isBlank())` 只在为空时才覆盖，改为**有效时才覆盖**

```java
// 修改前（有 bug，AI 返回错误 topic 时不会纠正）
if (sr.getTopic() == null || sr.getTopic().isBlank()) {
    sr.setTopic(defaultTopic);
}

// 修改后（defaultTopic 有效时始终覆盖，无效时才用 AI 返回值兜底）
if (defaultTopic != null && !defaultTopic.isBlank()) {
    sr.setTopic(defaultTopic);   // 不信任 AI 的判断，始终用后端传入的真实方向
} else if (sr.getTopic() == null || sr.getTopic().isBlank()) {
    sr.setTopic("未知方向");     // defaultTopic 为空时的最后兜底
}
```

**⚠️ 为什么不能直接写 `sr.setTopic(defaultTopic)`：**  
`scoreAnswerAsync(chatId, "", lastQuestion, message)` 这个调用（`QuizApp.java` 第 141 行）传入的 `defaultTopic` 是空字符串。如果无条件覆盖，topic 会被设为 `""`，反而比现在更差——评分会记录到空 key 下，画像数据完全失效。

#### 3.4 增加方向内部状态追踪

在 `SessionState` 中增加：
```java
final Map<String, Set<String>> topicCoveredDimensions = new HashMap<>();  // 方向 → 已覆盖维度
```

每次 AI 出题完成后，从 AI 回复中提取/推断本题属于哪个维度（简单 keyword matching 即可），标记为已覆盖。下一轮注入 prompt 时告知 AI 哪些维度还没有考察过。

## 问题四：能力画像薄弱点展示优化（折叠展开 + 知识点归属修正）

### 现状分析

`AbilityPanel.vue` 中，薄弱方向的 `weakPoints` 列表直接用 `<ul>` 全部展开显示，存在两个问题：
1. 知识点全部平铺在页面，视觉很拥挤
2. 由于问题三中 topic 归属混乱，JVM 下可能出现 Redis/并发等其他方向的知识点

### 改进方案

#### 4.1 折叠展开交互（参考 Ant Design Collapse 组件思路）

在 `AbilityPanel.vue` 中为每个薄弱方向加入折叠/展开状态：

```javascript
// ⚠️ 必须用 reactive() 包裹 Set，ref(new Set()) 无法追踪 .add()/.delete() 的变化
// 因为 Vue 3 的响应式系统追踪的是对象引用，Set 内部变化不会触发更新
const expandedTopics = reactive(new Set())

const toggleTopic = (topicName) => {
  if (expandedTopics.has(topicName)) {
    expandedTopics.delete(topicName)
  } else {
    expandedTopics.add(topicName)
  }
}
```

模板改为：
```html
<!-- expandedTopics 是 reactive Set，直接调用 .has() 即可触发响应式更新 -->
<div class="dir-header" @click="toggleTopic(t.topic)" style="cursor: pointer">
  <span class="dir-name">{{ t.topic }}</span>
  <span class="dir-level">{{ t.scoreEmoji }} {{ t.scoreLevel }}</span>
  <span class="collapse-icon">{{ expandedTopics.has(t.topic) ? '▲' : '▼' }}</span>
</div>
<!-- 薄弱点列表：只在展开时显示 -->
<transition name="collapse">
  <ul v-if="expandedTopics.has(t.topic) && t.weakPoints.length > 0" class="weak-points">
    <li v-for="wp in t.weakPoints" :key="wp">{{ wp }}</li>
  </ul>
</transition>
```

效果：点击 "JVM 🔴 薄弱" 才展开具体的薄弱知识点列表，不点击时只显示一行摘要。

#### 4.2 薄弱点数量徽标

在折叠状态下，在方向名右侧显示薄弱点数量徽标：

```html
<span class="weak-count-badge" v-if="t.weakPoints.length > 0">
  {{ t.weakPoints.length }} 个薄弱点
</span>
```

#### 4.3 知识点归属修正（配合问题三的修复）

解决方案已在问题三第 3.3 节说明：强制用后端传入的 `defaultTopic` 覆盖 AI 返回的 topic，从根源上避免跨方向污染。

前端展示侧无需额外改动，问题会随后端修复自然消失。

#### 4.4 薄弱点去重

`UserAbilityProfile.TopicScore.updateWeakPoints()` 在更新薄弱点时可能追加重复项，建议改为 `LinkedHashSet` 去重后再转 List，保留顺序且无重复。

| 🔴 P0 | 问题三 3.3：修复 topic 归属（3 行代码）| 极小 | 立即消除知识点归属混乱，且不引入空 topic 副作用 |
| 🔴 P1 | 问题二 方案A：禁用联网搜索 | 小 | 首 Token 延迟降低 0.5-1s，消除网络不确定性 |

| 🟡 P2 | 问题三 3.1：已问题目去重（从 AI 回复中提取指纹）| 中 | 降低重复率，不误判未问题目 |
