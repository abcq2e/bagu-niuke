## 📚 基础补充：四个核心指标详解

文档定义了 RAGAS 的三个维度四个指标：

### 检索质量指标

#### Context Precision （ 上下文精确率 ） 

```
问题：检索到的 5 个文档中，相关的排在前面了吗？

如果你检索了 5 个 chunks，其中 2 个相关：
- 排在 1、2 位 → Precision 高 ✓
- 排在 4、5 位 → Precision 低 ✗
```

> 通俗理解：有用的信息排得越靠前越好

#### Context Recall（上下文召回率）

```
问题：回答问题需要的信息，检索到了多少？

- 把参考答案拆成多个"声明"
- 判断每个声明是否能从检索结果中找到依据
- 被支持的声明占比 = Recall
```

> 通俗理解：应该检索到的信息，有没有漏掉

### 生成质量指标

#### Faithfulness（忠实度）

```
问题：LLM 生成的答案，有没有瞎编？

- 从答案中提取所有"声明"
- 验证每个声明是否能从检索上下文中找到依据
- 找不到依据的 = 幻觉
```

> 通俗理解：答案是不是"有据可查"

#### Answer Relevance（答案相关性）

```
问题：答案是否直接回应了问题？

方法：用答案反向生成问题，看生成的问题和原问题有多相似
```

> 通俗理解：答非所问的程度

## 🏗️ 动手升级：第 2 步 — 实现 Context Precision

这是 4 个指标中最直观的一个，先从它入手。

### 算法思路

```
输入：query, 检索到的文档列表（按分数排序）

1. 对每个检索到的文档，判断它是否与 query 相关
2. 计算 Precision@K：前 K 个结果中相关文档的占比
3. 对每个 K 加权平均（因为排在前面的更重要）
```

### 引导问题

1. 怎么判断一个文档是否与 query 相关？你可以用 LLM 来判断，也可以用简单的关键词匹配。哪种更准确？哪种更快？
2. 加权平均时，排名靠前的权重应该更大还是更小？怎么设计权重函数？

> **你的任务 2**：实现 Context Precision 的计算逻辑。建议先写一个简单的版本（比如用关键词密度判断相关性），再考虑用 LLM 判断。

## 🏗️ 动手升级：第 3 步 — 实现 Faithfulness（核心挑战）

这是 4 个指标中最重要的，也是最有挑战的。

### 算法思路

```
输入：LLM 生成的答案, 检索到的上下文文档列表

Step 1: 用 LLM 从答案中提取所有"声明（claims）"
    Prompt: "请从以下文本中提取所有事实性声明，每行一个：{答案}"

Step 2: 对每个声明，用 LLM 判断是否能从上下文中推断出来
    Prompt: "请判断以下声明是否可以从给定上下文中推断出来：
             声明：{claim}
             上下文：{context}
             只回答 YES 或 NO"

Step 3: Faithfulness = YES 的数量 / 总声明数
```

### 引导问题

1. Step 1 和 Step 2 都调用了 LLM，这是一笔不小的开销。你觉得可以用什么办法减少调用次数？
2. 如果答案中包含代码块，怎么提取其中的"声明"？
3. 声明提取的 Prompt 直接决定了评估质量。你能设计一个更好的 Prompt 吗？

> **你的任务 3（核心）**：实现 Faithfulness 的计算逻辑。这是整个评估体系中最关键的部分。

## 🏗️ 动手升级：第 4 步 — 集成到测试中

评估不是一次性的，应该是 **持续进行** 的。每当你调整了切分参数、换了检索策略，都应该跑一次评估。

### 引导问题

1. 你会把评估代码放在哪里？`src/test/java` 下还是 `main` 下？
2. 评估数据（问题 + 检索结果 + 答案）怎么准备？手动写还是自动采集？

> **你的任务 4**：编写一个测试类，选取 5-10 个代表性问题和对应的知识库内容，评估当前系统的 RAGAS 指标，作为 baseline。

## 💡 延伸思考

文档提到了 ICLERB（In-Context Learning Embedding and Reranker Benchmark）的思路：

> 语义相似 ≠ 对 LLM 有用。检索候选文档 → 注入 LLM 生成答案 → 评估答案准确性 → 反推检索器效果

这和 RAGAS 的区别是什么？RAGAS 评估的是"检索结果本身"，ICLERB 评估的是"检索结果对 LLM 的帮助有多大"。你更认同哪一种？
