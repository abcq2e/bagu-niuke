## 📖 先读这个：你凭什么说 Agent"变好了"？

你现在有了 RAG 评估（`RagasEvaluator`），知道检索质量是好是差。但 Agent 本身呢？

改了一行 Prompt → "感觉回答更好了"
换了一个 Tool → "好像调用更准确了"
加了 Plan-and-Execute → "看起来更有条理了"

全是"感觉"。文档《落地实践.md》一句话打脸：

> 不用数据说话，优化就是自我安慰。

文档来自腾讯 TEG 网关测试团队（真名实姓的工程实践），他们面对的是真正的生产环境 Agent。
他们的核心观点：

> Agent 的非确定性、黑盒化、错误级联放大——这三个问题让"感觉"成为最不可靠的评判标准。

但他们也给出了完整的解决方案：一套可工程化的评估体系。

> 测评的目标是建立一个可重复、可量化、可持续演进的评估闭环，而不是追求完美覆盖。
> 关键在于：每次变更都能快速跑出一个可比较的分数。

本篇教程基于这套方法论，帮你从零搭建 Agent 评估体系。

## 📚 基础补充：评估体系的三个核心概念

### 概念 1：三类评委（谁来评？）

文档设计了一个分层评分体系：

```
┌──────────────────────────────────┐
│      确定性评分器（代码）            │  ← 主力，快、便宜、客观
│   脚本/Bash/正则/断言              │     负责所有"能用代码判断"的事
└──────────────────────────────────┘
              ↑
┌──────────────────────────────────┐
│      Rubric 评分器（LLM）          │  ← 扩展，灵活、可扩展
│   LLM-as-Judge + Prompt + Schema │     负责"代码搞不定但能结构化描述"
└──────────────────────────────────┘
              ↑
┌──────────────────────────────────┐
│      人工评分器（专家）              │  ← 兜底，贵、慢、黄金标准
│   领域专家                         │     负责校准、诊断、边缘场景
└──────────────────────────────────┘
```

**选择优先级**：确定性评分器 > Rubric 评分器 > 人工评分器

### 概念 2：五个评估维度（评什么？）

| 维度 | 问题 | 优先级 |
|------|------|--------|
| 功能正确性 | Agent 做对了吗？ | P0 必须 |
| 鲁棒性 | Agent 会不会在关键时刻翻车？ | P0 必须 |
| 过程质量 | 过程合理吗？（还是碰巧对了？） | P1 |
| 效率成本 | 划算吗？Token 消耗合理吗？ | P1 |
| 体验对齐 | 用户愿意继续用吗？ | P2 |

### 概念 3：基线（Baseline）是什么？

文档给了一个很重要的概念：

> 用例基线是单个用例执行 1 次后，经人工确认的预期过程和预期结果的快照。
> 它回答的是："这个用例，正确的执行应该长什么样？"

```
用例 = Prompt + 检查规则
基线 = 人工确认过的"正确答案"（包含预期过程 + 预期结果）

每次改代码后：
  跑同一个用例 → 拿新结果跟基线对比 → 看出差异 → 打分
```

## 🏗️ 动手升级：第 1 步 — 设计评估用例模型

评估的第一步是定义"测什么"。文档用 YAML 来管理用例集，你需要先用 Java 类来表达这个结构。

### 引导问题

1. 一个评估用例包含什么信息？
   - 用例名称（如"搜索Java教程"）
   - 输入的 Prompt（如"帮我搜一下Spring AI最新教程"）
   - 期望的结果（什么才算"正确"？）
   - 检查规则（怎么验证"正确"？）

2. "期望的结果"可以很复杂。有时候你期望"回答中包含某个关键词"，有时候你期望"调用了工具 X"，
有时候你期望"工具调用次数不超过 5 次"。这些不同的"期望"怎么用 Java 类统一表达？

3. 文档用 YAML 管理用例。你打算用什么？YAML？JSON？还是直接硬编码在 Java 测试类中？

> **你的任务 1**：创建 Agent 评估用例的数据模型。
>
> 🔴 在 `evaluation/` 包下创建：
> - `AgentEvalCase.java` — 评估用例（name + prompt + expectedBehavior）
> - `ExpectedBehavior.java` — 期望行为（工具调用检查 + 关键词检查 + 效率约束）
>
> 💡 `ExpectedBehavior` 是关键设计——想想怎么表达"应该调用了 searchWeb 工具"、"
> 回答应该包含 Spring 这个词"、"工具调用次数不超过 5 次"这些约束。

## 🏗️ 动手升级：第 2 步 — 实现确定性评分器

确定性评分器 = 用代码自动判断对错。这是你评估体系的主力，P0 维度全靠它。

文档中的确定性评分器示例：

```yaml
expected_behavior:
  # 过程检查：是否调用了指定工具
  -tool_call: "webSearch"
     contains: "Spring"
  # 结果检查：回答是否包含关键信息
  -response_contains:
     - "Spring AI"
     - "教程"
  # 效率检查：工具调用次数上限
  -max_tool_calls: 5
```

### 引导问题

1. 你已经有 `AgentTrace`（第 7 篇），Trace 里记录了每一步的工具调用。你怎么从 Trace 中提取"工具调用列表"？
2. 怎么判断工具调用是否包含某个关键词？
   - 💡 提示：`String.contains()` 够用吗？大小写敏感怎么办？
3. 怎么统计工具调用次数？从 Trace 的 `steps` 里过滤出"工具调用"类型的步骤？
4. 每个检查的返回值是什么？`boolean`（通过/不通过）？还是 `int`（扣x分）？

> **你的任务 2（核心）**：实现 `DeterministicScorer` 确定性评分器。
>
> 🔴 你需要做：
> - ① 写一个 `checkToolCall(String toolName, String expectedContent)` 方法：检查是否调用了指定工具，且参数/结果包含期望内容
> - ② 写一个 `checkResponseContains(List<String> keywords)` 方法：检查最终回答是否包含所有关键词
> - ③ 写一个 `checkMaxToolCalls(int maxCalls)` 方法：检查工具调用次数是否超标
> - ④ 综合打分：满分 100，扣分制，每个检查不通过扣 N 分
>
> 💡 扣分标准自己定，但要能用数据解释"为什么扣了这么多"。

## 🏗️ 动手升级：第 3 步 — LLM-as-Judge（Rubric 评分器）

有些东西代码判断不了——"回答的推理逻辑是否合理"、"有没有幻觉"——这些需要 LLM 来判断。

文档叫它 "Rubric 评分器"：

> Rubric 评分器灵活、可扩展，负责"代码搞不定但能结构化描述"的场景。

你其实已经写过类似的东西了！`RagasEvaluator` 中的 `extractClaims()`
和 `verifyClaimByContext()`
就是"让 LLM 当评委"。Rubric 评分器就是这个思路的系统化。

### 引导问题

1. Rubric 评分器给 LLM 的 Prompt 需要包含什么？评判标准？评分维度？输出格式？
2. LLM 的打分结果怎么解析？你要求 LLM 返回 JSON（`{"score": 85, "reason": "..."}`），还是纯数字？
3. LLM 可能有自己的偏好（"回答长就是好"）。你怎么减少这种偏差？文档中提到了什么技巧？
4. Rubric 评分器的成本很高（每次打分都要调 LLM）。你怎么控制成本？只对关键用例使用？

> **你的任务 3（进阶）**：实现 `RubricScorer` LLM 评分器。
>
> 🔴 你需要做：
> - ① 设计评分 Prompt：告诉 LLM 评判标准和输出格式
> - ② 调 LLM，解析返回的分数
> - ③ 重点检测"幻觉"——回答中是否包含检索结果中找不到的信息
>
> 💡 你的 `RagasEvaluator.extractClaims()` + `verifyClaimByContext()`】
> 就是检测幻觉的现成工具。可以把它们复用为 Rubric 评分器的一部分。

## 🏗️ 动手升级：第 4 步 — 基线管理与回归测试

有了用例和评分器，还需要"参考答案"（基线）和"对比流程"（回归测试）。

基线本质上就是一个**人工确认过的快照**：对一个用例跑一次，人工验证"这个结果是正确的"，然后把分数和期望行为存下来。以后每次改代码，拿新结果跟基线对比，分数跌了 → 改坏了。

### 引导问题

1. 基线的建立流程：**跑一次 → 人工确认 → 保存为基线**。你的基线数据存哪里？
   - JSON 文件（简单直接，适合小规模）
   - 数据库（适合大规模、多版本管理）
   - 💡 建议先用 JSON 文件跑通流程，后面量大了再迁数据库
2. 什么时候需要更新基线？
   - ✅ 模型升级了（GPT-4 → GPT-5）→ 重新建基线
   - ✅ Prompt 大改 → 旧基线不再适用
   - ✅ 新增了工具 → 预期行为可能变化
   - ❌ **不要**因为"分数跌了"就改基线来让分数好看——那是掩耳盗铃
3. 回归测试的流程：**加载用例 → 跑 Agent → 评分 → 对比上次分数**。
   如果分数下降超过阈值（比如 10%），说明最近的改动有回归问题。
4. 基线数据结构长什么样？最小字段：
   - `caseName`：用例名称
   - `query`：用户问题
   - `createdAt`：基线建立时间
   - `expectedBehavior`：期望行为（ExpectedBehavior 对象）
   - `baselineDeterministicScore`：确定性评分（人工确认过的）
   - `baselineRubricScore`：Rubric 评分（人工确认过的）
   - `notes`：备注（如"基于 GPT-4o 2026 版本建立"）

> **你的任务 4**：建立基线管理机制。
>
> 🟢 已为你生成：
> - `BaselineManager.java` — 骨架代码已写好（保存/加载/对比方法 + Baseline + ComparisonReport 数据模型）
> - `evaluation/baselines/` 目录已创建
>
> 🔴 你需要做：
> - ① 选 3 个代表性用例，手动跑一次 Agent，人工确认结果正确
> - ② 用 `BaselineManager.saveBaseline()` 把确认后的结果保存为基线 JSON 文件
> - ③ 改一行 Prompt（比如调整 System Prompt），跑回归测试：
>      ```
>      Baseline baseline = manager.loadBaseline("用例名");
>      EvaluationResult newResult = runAgentAndScore(case);
>      ComparisonReport report = manager.compareWithBaseline("用例名", newResult);
>      System.out.println(report);
>      ```
>      看分数是涨了还是跌了，用数据（不是感觉）判断改动是否有效
>
> 💡 这是整个评估体系的"最后一公里"——没有基线，评分没有参照物。

## 🏗️ 动手升级：第 5 步 — 稳定性评估（pass^k）

文档引入了 `pass^k` 概念：

> pass^k：k 次试验中每次都通过的概率，衡量稳定性。
> pass@k：k 次中至少 1 次通过的概率，衡量峰值能力。

对 Agent 来说，"偶尔能跑通"和"每次都跑通"是天壤之别。

### 引导问题

1. 同一个用例，连续跑 3 次（或 5 次），结果一致吗？工具调用序列一样吗？
   - LLM 的非确定性意味着每次输出都有细微差异。稳定性测试帮你量化这种差异有多大。
2. 如果 3 次中 2 次成功 1 次失败，pass^3 = 2/3 ≈ 67%——你的 Agent 不够稳定。
3. 文档对不同 Agent 类型给了不同的容忍阈值：
   - 关键决策类（金融、医疗、安全）：**0%**（必须全部通过，一次都不能失败）
   - 辅助分析类（搜索、总结、翻译）：**≤ 10%**
   - 创意生成类（写作、绘图）：**≤ 30%**
   - 💡 你的知识库 Agent 属于"辅助分析类"→ 容忍失败率 ≤ 10%
4. 除了"通过/失败"的二元判断，**分数波动**也很重要。
   - 同一用例跑 5 次，分数分布是 85/86/84/85/85（标准差小）还是 90/60/80/55/85（标准差大）？
   - 前者说明 Agent 行为稳定，后者说明 Agent 行为随机——可能是 Prompt 不够约束或某个 Tool 不稳定。
5. 稳定性测试的设计模式：**在外部用 for 循环调用，跟 Agent 代码解耦**。
   ```
   for (int i = 0; i < 5; i++) {
       AgentTrace trace = agent.run(query);
       ScoreResult score = scorer.score(trace, expectedBehavior);
       // 收集分数...
   }
   // 统计 pass^k、平均分、标准差
   ```

> **你的任务 5**：实现稳定性测试。
>
> 🟢 已为你生成：
> - `StabilityTester.java` — 完整代码已写好（test 方法 + StabilityReport + TestResult）
>
> 🔴 你需要做：
> - ① 用 `StabilityTester` 对同一个用例连续跑 N 次（建议 N=5）
> - ② 观察 `StabilityReport`：
>      - `passK`：通过率，越高越好
>      - `avgScore`：平均分
>      - `stdDev`：标准差，越小越稳定
>      - `isStable`：是否稳定（失败率 ≤ 10%）
> - ③ 如果发现不稳定（`isStable = false`），排查原因：
>      - 是不是某个 Tool 有时返回空结果？
>      - 是不是 Prompt 描述不够精确导致 LLM 犹豫？
>      - 是不是 Agent 的推理步骤太多，存在"走偏"的概率？
> - ④ 改进后重新跑稳定性测试，确认 `passK` 提升
>
> 💡 这个任务跟你的 `BaseAgent.run()` 解耦 — 在外部用 for 循环调用就行了。
>    `StabilityTester` 通过 `Supplier<TestResult>` 接收你的执行逻辑，完全不用改 Agent 代码。
