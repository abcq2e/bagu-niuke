### 4.0.1 ⚠️ 「10 分阈值」被实测证伪，已改成 Rubric 不参与判定

建基线当天同一个 commit 连跑两轮，**代码一行没改**：

| 用例 | Rubric 第一轮 → 第二轮 | Δ |
|---|---|---|
| 多工具串联 | 60 → 50 | **−10** |
| 对比SpringAI与LangChain4j | 63 → 76 | **+13** |
| 工具失败自愈 | 94 → 100 | +6 |
| 知识库RAG检索 | 55 → 60 | +5 |
| 文件读写往返 | 100 → 100 | 0 |
| **确定性分数（6 条全部）** | — | **全部 Δ=0** |

**Rubric 的噪声（±13）已经与要检测的信号同量级**，10 分容差盖不住，
第二轮就误报了一次「改坏了」。`RegressionPolicy` 的类注释当初就写过这个风险的
应对方式：*阈值调到能吞下噪声，等于关掉这项检查*。

**已按用户决定改为**：回归只由确定性分数判定（`isRegressed` 只看 `deltaDeterministic`）；
Rubric 降为参考信息，`RUBRIC_REGRESSION_THRESHOLD`(10) 改成
`RUBRIC_NOTEWORTHY_DELTA`(15)，语义从「回归阈值」变为「值得看一眼的提示阈值」，
**不影响退出码**。类注释里完整记录了实测数据与这条弯路。

**知情取舍**：模型质量明显下降、但规则分恰好不变的场景会漏报。要覆盖它，
需要提升 Rubric 打分的稳定性（`StabilityTester` 重复采样取中位数），
而不是把不稳定的一次采样接进阻断判定。**这是后续可做的方向。**

### 4.0.2 顺带修掉的两个真实 bug

跑基线时发现「搜索Spring AI教程」打分正常却始终建不了基线，查出：

1. **`BaselineManager.toFilePath` 会把空格换成 `_`**，而磁盘上那份文件名是带空格的
   → 按净化名永远找不到文件 → 静默走进「用例文件不存在」分支 → 永不建基线。
   修法：新增 `resolveFile`，先试净化名，找不到再按文件内 `caseName` 字段扫目录匹配；
   load 与 save 都走它。
2. **`EvalReport.render` 把「用例文件不存在」的告警静默吞掉** —— 渲染分支只在
   「新建基线」或「有基线可对比」时打印 summary，其余什么都不打印。
   这正是上面那个 bug 藏了这么久没被发现的原因。

两条都有测试 + 变异验证。

### 4.1 这个方向的核心设计（面试亮点）

`BaselineManager` 已把 Rubric 纳入判定，但 `EvalReport.hasRegression()` 只看 deterministic ——
**同一份报告里正文说"改坏了"、结论说"无回归"**。修法不是"加上 Rubric"，而是把判定**收拢到一处**。
阈值语义：确定性分数**任何下降**都算回归（规则打分无方差）；Rubric **降幅 ≥10 分**才算
（LLM 打分有方差，用 `<0` 会噪声淹没真信号）。

### 4.2 Task 5 必须做的事（有人工环境时）

不只是「跑一次建基线」。**有一条计划没覆盖但必须验证的东西**：

**⚠️ 验证「退出码透传」这条链路真的成立。**
`EvalRunner` 调 `System.exit(exitCode)`，但 `scripts/eval-regression.sh` 是用
`./mvnw -q spring-boot:run -Peval` 跑的，而 `spring-boot:run` **默认 fork 子 JVM** ——
子进程的退出码能不能成为 maven 的退出码，**从未验证过**。若不成立，
回归检查会**永远显示成功**（假绿），整套机制形同虚设。
做法：照计划的完成标准，**临时把某条基线的 `baselineDeterministicScore` 调高 20 分**，
重跑脚本，确认 `exit=1` 且报告说「分数下降」；然后改回。

其余照计划走：Task 5 Step 1–6（首次运行自动建基线 → 人工审查别照单全收 → 改 `notes` 为已确认 → 复跑）。
**另外**：`autoEstablishBaseline` 会把 `notes` 整段重写为「🆕 自动建立于…」，
计划里精心写的用例意图说明会**被清掉**，且 `saveBaseline` 用 pretty-printer 重写整个文件（diff 会很大）。
跑完记得把 `notes` 人工补回。

## 6. 执行方式建议

沿用 **`superpowers:subagent-driven-development`**：每个任务派一个干净子 Agent，
任务间做规格 + 质量两阶段复审。

关键做法（本轮实测有效）：
- 派发实现者时**把任务的完整文本贴进 prompt**，不要让子 Agent 去读计划文件
- 子 Agent 只 `git add` 指定的文件，**绝不用 `git add -A`**（工作区常有用户的未提交改动）
- 每个任务后跑**相关**测试，不要跑全量
- 复审时明确要求做**变异验证**，并在 prompt 里写出期望的失败信息形态

按严重程度排序，都不是阻塞项：

2. **`QueryRewriter`**：同样未加哨兵识别，兜底话术会被当成改写后的查询，导致 RAG 检索质量下降
   （不会产生脏数据，只是降级）。
3. **其它 `doOnComplete` 保存模式**：`QuizApp.java:562` 的 `doOnComplete` 内含
   `scoreAnswerAsync` 与游标推进 `markQuestionAsked`，**SSE 断线时不触发** ——
   与 Task 7 修的是同一类问题，但会牵涉评分与游标的一致性，未在本轮处理。
   `WrongQuestionReviewService.java:156`、`graph/listener/ConversationGraphAdvisor.java:137` 同理。
4. **`config ↔ agent.llm` 包循环**：`config/ResilientChatModelConfig` 依赖 `agent.llm`，
   而 `agent.llm` 依赖 `config.LlmResilienceProperties`，构成双向依赖。
   `PackageDependencyTest` 的规则目前不覆盖 `config` 包，所以没红。无运行时影响。
5. **`docker-compose.light.yml` 没有 `eval_data` volume**（`prod` 有）—— 既有不对称，本轮未动。
6. **`.active-specs/` 没有数量上限**：用户长期不删会话时目录只增不减（与 `.quiz-cursor` 等现状一致）。
