## 0. 这台服务器的真实架构（动任何命令前必读）

**关键认知：服务器不是 docker-compose.prod.yml 描述的"全家桶"，而是"compose 应用 + 外部手工数据库"的混搭。** 这是以往"一更新就炸"的总根源。

### 0.1 服务与容器清单

| 服务 | 容器名 | 镜像 | 端口(宿主) | 归属 | 网络 |
|---|---|---|---|---|---|
| 后端 Spring Boot | `qian-backend` | `qian-ai-agent-qian-backend` | 8123 | compose 项目 `qian-ai-agent` | `qian-ai-agent_qian-net` |
| 前端 Nginx | `qian-frontend` | `qian-ai-agent-qian-frontend` | 80 | compose 项目 `qian-ai-agent` | **曾分裂**，需并入同一网络 |
| 图数据库 | `qian-neo4j` | `neo4j:5` | 7474/7687 | compose | compose 网络 |
| 向量库 | `qian-pgvector` | `pgvector/pgvector:pg16` | - | compose | compose 网络 |
| **MySQL（真实业务库）** | `mysql` | `xfg-studio/mysql:8.0.32` | **13306** | **外部手工容器，不属于 compose** | 手工 `connect` 进 compose 网络 |
| **Redis** | `redis` | `xfg-studio/redis:6.2` | **16379** | **外部手工容器，不属于 compose** | 手工 `connect` 进 compose 网络 |
| 其它无关服务 | phpmyadmin/rabbitmq/ollama/nacos/xxl_job 等 | - | - | 与本文项目无关 | - |

### 0.2 必须记住的三点

1. **compose 里定义的 `qian-mysql`、`qian-redis` 两个数据库服务从未在这台机器上 up 过**。真正的库是外面的裸容器 `mysql`(13306)、`redis`(16379)。后端通过**网络别名** `qian-mysql`/`qian-redis` 访问它们。
2. **后端依赖 4 个服务名**：`qian-pgvector`、`qian-neo4j`、`qian-mysql`、`qian-redis`。它们必须全部能和 `qian-backend` **处在同一个 docker 网络**里，否则后端启动直接 `UnknownHostException` 反复重启。
3. 代码部署目录是 `/opt/qian-ai-agent`（有 `.git`，可 `git pull`）。**别在 `/root` 下找，也别再整目录手工拷文件上去**（会把隐藏数据目录和版本一起搞乱）。

## 2. 日常「更新后端」的标准流程（照着做就不会炸）

前置：代码改动先在本机 `git commit` 并 **`git push`** 到远程，服务器用 git 拉，**不要 scp 整个目录**。

```bash
# ① 进服务器项目目录（不是 /root）
cd /opt/qian-ai-agent

# ② 拉最新代码（确认 remote 是你的仓库）
git pull

# ③ 构建并重启后端（等价 update.sh backend）
bash scripts/update.sh backend

# ④ 关键一步：每次重建后端容器后，网络关系不会自动恢复，
#    必须补一次"网络自修复"，否则必现 UnknownHost / 502
bash fix-net.sh        # 脚本见第 3 节，提前放好
#    或手动执行第 3 节等价命令

# ⑤ 验证三连
docker ps | grep qian-backend                  # STATUS 不是 Restarting/Exited
curl -s http://localhost:8123/api/actuator/health | head -c 120   # 非 502 即可，DOWN 只是 DeepSeek key
curl -s -X POST http://localhost:8123/api/user/login -H "Content-Type: application/json" \
     -d '{"username":"<真实账号>","password":"<真实密码>"}'        # 应返回 code:0 + token
```

> 💡 后端数据都在卷里，容器重建**不会丢数据**；丢的只是"容器与依赖的网络关系"——这就是第 ④ 步存在的意义。

## 3. 网络自修复脚本（服务器上必备）

把下面内容保存为服务器 `/opt/qian-ai-agent/fix-net.sh`，并 `chmod +x fix-net.sh`。
仓库模板：`docs/ops/fix-net.sh`。

```bash
#!/bin/bash
# 每次 update.sh backend/frontend 之后执行，把依赖容器全部并入 backend 网络
set -u
NET=qian-ai-agent_qian-net

echo "== 将 pgvector / neo4j / frontend 并入 $NET =="
for c in qian-pgvector qian-neo4j qian-frontend; do
  docker network connect "$NET" "$c" 2>/dev/null && echo "  + $c" || echo "  = $c (已连接或跳过)"
done

echo "== mysql/redis 以后端期望的名字接入（带别名）=="
# 已带别名则跳过；未连接则直接连；仅同名则断开重连加别名
docker network inspect "$NET" >/dev/null 2>&1 || { echo "网络 $NET 不存在，先 up 一次 compose"; exit 1; }
for pair in "mysql:qian-mysql" "redis:qian-redis"; do
  real="${pair%%:*}"; alias="${pair##*:}"
  if docker network inspect "$NET" --format '{{range .Containers}}{{.Name}} {{end}}' | grep -qw "$alias"; then
    echo "  = $real 已以 $alias 接入"
  else
    docker network disconnect "$NET" "$real" 2>/dev/null
    docker network connect --alias "$alias" "$NET" "$real" && echo "  + $real -> alias $alias"
  fi
done

echo "== 重启应用容器让解析生效 =="
docker restart qian-backend qian-frontend
echo "done. 之后请 curl http://localhost:8123/api/actuator/health 验证。"
```

## 5. 常见问题速查表

| 症状 | 根因 | 处理 |
|---|---|---|
| 后端日志 `java.net.UnknownHostException: qian-pgvector / qian-mysql ...`，反复重启 | 后端与依赖不在同一网络 | `bash fix-net.sh` |
| 浏览器访问登录 → **502** | `qian-frontend` 与 `qian-backend` 不在同一网络，nginx 解析不到 | `docker network connect qian-ai-agent_qian-net qian-frontend && docker restart qian-frontend` |
| 浏览器提示"服务器错误稍后重试" | 先用 curl 直连后端区分层 | `curl -X POST .../api/user/login` 能通=后端好，问题在 nginx/前端；再查 `docker logs qian-backend` |
| `curl .../login` 返回 `Required request body is missing` | curl 命令被换行拆坏、没带 body | 命令写成**单行**再执行 |
| 后端 health 总 `DOWN` | 多为 `deepSeek: DOWN` = **API Key 失效(401)** | 见第 6 节更新 key |
| AI 功能(点评/画像/Agent)报 401 / Authentication Fails | DeepSeek/DashScope Key 失效或被风控 | 更新 `.env` 中对应 key → `update.sh backend` |
| 登录能进但"历史数据空" | 数据按 `user_<id>` 存，历史在 **`qian`(id=1)** 名下 | 用 `qian` 账号登录；其它账号无历史属正常 |
| 构建镜像报 `docker.xuanyuan.me ... 403` | 服务器拉取镜像被加速源拒 | `docker pull docker.m.daocloud.io/<镜像>` 后 `docker tag` 成本地名再 build |
| 忘了有没有危险命令 | — | 确认不含 `down -v` / `volume prune` / `rm -f` 再执行 |

## 6. 备份与恢复（强烈建议定期做）

### 6.1 MySQL（用户/会话等库数据）
```bash
mkdir -p /opt/backups
docker exec mysql sh -c 'exec mysqldump -uroot -p"<密码>" --databases qian_ai_agent' > /opt/backups/mysql_qian_ai_agent_$(date +%Y%m%d).sql
```

### 6.2 文件型数据（画像/进度/错题/正文 —— 重点是这几个卷）
任选可用镜像（服务器上有 `amazoncorretto:21-alpine`，无需再拉）：
```bash
BK=/opt/backups && mkdir -p $BK
for v in ability_profiles quiz_cursor review_cursor chat_memory; do
  docker run --rm -v qian-ai-agent_$v:/data -v $BK:/bk \
    amazoncorretto:21-alpine sh -c "tar czf /bk/${v}_$(date +%Y%m%d).tgz -C /data ."
done
ls -lh $BK
```

### 6.3 恢复（示例：ability_profiles）
```bash
docker run --rm -v qian-ai-agent_ability_profiles:/data -v /opt/backups:/bk \
  amazoncorretto:21-alpine sh -c "tar xzf /bk/ability_profiles_XXXX.tgz -C /data"
docker restart qian-backend
```

## 7. 血泪原则（本次 2026-09 事故复盘出的红线）

1. **代码走 git，绝不整目录手工拷贝上服务器**。上次就是把本机隐藏数据目录 + 代码一起拷上去，导致版本与数据归属都难追溯。
2. **容器重建 ≠ 数据丢失，但 = 网络关系重建**。重建后端/前端后，第一件事补 `fix-net.sh`。
3. **动手前先备份**（尤其涉及 compose down / 卷 / 网络时）。
4. **搞清楚数据在哪个账号下**。文件按 `user_<id>` 存，看"没数据"先确认登录账号的 id 对不对得上（本机历史在 `qian`=1）。
5. **health DOWN 不一定是故障**：本机 health 长期 DOWN 仅因 `deepSeek` key 未配好，`db/redis/neo4j/pgvector` 全 UP 即核心可用。
6. 别在 `/root` 或错误目录执行服务器命令；项目真实目录是 `/opt/qian-ai-agent`。

## 附录：本次事故时间线（2026-09 复盘，供后人少踩坑）

1. `update.sh backend` 重建 `qian-backend` → 容器落入新网络 `qian-ai-agent_qian-net`。
2. 后端启动报 `UnknownHostException: qian-pgvector` 反复重启 —— 因为 pgvector/neo4j/mysql/redis 不在该网络。
3. 手动将 `qian-pgvector`、`qian-neo4j` connect 进网络；`mysql`/`redis` 需**带别名** `qian-mysql`/`qian-redis` 接入（先 disconnect 再 connect --alias）。
4. 后端恢复启动成功。
5. 浏览器访问报 502 —— `qian-frontend` 还在旧网络 `qian-net`，connect 进同一网络并重启后恢复。
6. 过程中误把"登录 500 / 数据空"归因于代码版本，实为：curl 换行破坏导致 `request body missing`(测试假象)、以及历史数据本就集中在 `qian`(id=1) 账号下。
7. 遗留项：`deepSeek` key 401 需更新；如后续收敛架构，建议把 mysql/redis 迁入 compose 全家桶统一管理，或长期维持外挂 + `fix-net.sh` 方案。
